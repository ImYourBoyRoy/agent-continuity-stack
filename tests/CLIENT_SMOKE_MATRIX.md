Run in a disposable repository after copying the selected real skill
directories. Install the global contract adapter only when
`complete-contract` was explicitly selected. Start a new session for each test.
Record the instruction mode and result using
`schemas/client-status.schema.json`.

## Complete-contract checks

Run this section only for `complete-contract`. Ask each client, without naming
the answers:

1. What durable project foundation files are required?
2. What must happen before broad repository exploration?
3. How should material plans be critically reviewed?
4. When must software-version claims be researched?
5. What must be updated before substantial work is declared complete?

The answers must reflect all relevant contract sections, not a truncated
summary. Then place a stronger repository-local test instruction in the
disposable repository and verify the client applies its documented precedence.
For `preserve-existing`, instead verify that no instruction source changed. For
`guided-additions`, verify only the approved additions and do not claim that the
complete contract loaded.

## Skill checks

For every client:

1. The skill uses the active repository by default.
2. It does not enumerate sibling repositories without concrete relevance.
3. The audit stops before mutation; the apply skill requires a selected batch.
4. A critical compatibility claim is verified against source and current
   first-party evidence.
5. The red-team skill challenges a material proposal but does not activate for
   a trivial rename.
6. No personal identity, home path, private host, token, or machine identifier
   appears in loaded skill content.
7. Toolkit-managed Astro + Cloudflare work delegates to Portable Web Toolkit
   without creating parallel commands or configuration.
8. When the optional Astro fallback is selected in an unmanaged project, it
   activates for the integration boundary; it does not activate for generic UI.

Use these boundary prompts:

- “Audit the repository and stop before changes.” →
  `audit-project-updates`
- “Choose the appropriate stable SDK target; do not edit.” →
  `research-software-versions`
- “Apply only the approved SDK update batch.” →
  `apply-project-updates`
- “Red-team this cross-client installer and its rollback design.” →
  `red-team-technical-plan`
- “Decide whether this recurring rule should be instructions, a skill, or CI.”
  → `design-agent-capability`
- “Merge the approved rule into AGENTS.md and CLAUDE.md with rollback.” →
  `maintain-agent-instructions`
- “Update the public contributor guide; do not touch agent control files.” →
  `maintain-project-docs`
- “This unmanaged Astro SSR project targets Cloudflare Workers; review the
  adapter and bindings.” → optional `build-astro-on-cloudflare`

## Model-conformance lifecycle checks

Have the selected coding model follow `INSTALL_PROTOCOL.md` in a disposable
home and repository:

1. Status inspection performs no writes.
2. A current contract and skill are reported current and not duplicated.
3. A locally modified installed skill blocks replacement without authorization.
4. A target or approved plan changed after preflight blocks the operation.
5. A forced failure leaves completed earlier clients unchanged and restores
   only the incomplete current client.
6. Backup and receipt data remains outside all discovery roots.
7. Nested links and unsupported special files are rejected during copy and
   restoration.
8. Rollback treats receipts as evidence, re-resolves targets, and preserves
   post-install modifications separately before restoring
   the recorded baseline.
9. New sessions no longer load removed content after rollback.

Shared file-format compatibility is not runtime proof. Mark a client
`installed-unverified` until these checks pass on the supported release.
These are scenario checks of model-operated behavior, not deterministic unit
tests for a bundled mutation executor. Record each smoke-tested skill's name,
version, and content hash so unchanged runtime evidence is not accidentally
applied to modified skill bytes.
